# M61 spot-check pack — for the owner

M61 (*Verifier Truth*) is the milestone that audits the machinery which proves
everything else. Its **verdict is yours** (IDE Honesty Contract §8 rule 5: the
gate proposes, the owner decides) — this pack is what to try, what each gate
proves, and what is known-not-done, so the verdict can be made on evidence
rather than on a green summary.

Everything below is machine-verified on every run: `npm run verify:fast` ends
with G1–V6, and `npx tsx script/m61/verify-closure.ts` (X1) re-earns the whole
bar at the current HEAD. Nothing in this pack asks you to take a number on
trust — each item names the command that produces it.

## 1. G1 — governance (issue #848)

- `npx tsx script/m61/verify-governance.ts`
- Proves: the ledger (`validation/m61/results/manifest.json`) validates whole
  (structure, closure rules, D-7 lane discipline); every trusted record verifies
  through the ONE sealed read path; the bar is **re-executed**, never cited;
  no gate leaves a lock behind; and the launch set is read from its owner module
  (D-5), not re-listed inline.
- **The number you should distrust and check**: the ledger's own entry. It is
  *derived* from `G1.json` on every run, never typed — the gate's drift check
  fails loudly if it ever is.

## 2. V1 — evidence sealing (issue #842)

- `npx tsx script/m61/verify-sealing.ts`
- Proves: every evidence write goes through one path carrying a sha256 seal, and
  a clobbered, truncated, or hand-edited record is REFUSED by the trusted read.
  Try it: edit any `validation/m61/results/V*.json` by hand (change a number) and
  re-run — the seal check names the record and refuses it.

## 3. V2 — gate serialization (issue #843)

- `npx tsx script/m61/verify-lock.ts`
- Proves: a declared lock per results directory; a second gate run against the
  same directory is refused **loudly** rather than clobbering the first; a
  stale lock is reported, never silently stolen. This is the fix for the
  concurrent-run cascade that produced contradictory evidence.

## 4. V3 — reproducibility (issue #844)

- `npx tsx script/m61/verify-reproducibility.ts`
- Proves: a declared sample of the lane's records REPRODUCE — the recorded
  command is re-executed inside a detached worktree of HEAD and the fresh record
  is diffed field-by-field against the stored one. A stored record that no
  longer reproduces fails here.

## 5. V4 — the verifier lint (issue #845)

- `npx tsx script/m61/verify-lint.ts`
- Proves: a gate that cannot fail is not evidence. Every lane gate declares what
  it produces, carries a can-fail proof, and is wired into a declared execution
  tier; every orphan record is either a real gate output or a declared artifact;
  every skip env-var is declared. Its census is the reason the M61 work found
  the gates nobody was running.

## 6. V5 — claim pins (issue #846)

- `npx tsx script/m61/verify-claims.ts`
- Proves: published numbers in `README.md`, the website, and `docs/` are
  re-derived from the ledgers they cite. On its first run it found real prose
  drift (the M26 and M28 claims) and corrected it; the byte-gate now keeps prose
  from drifting again.

## 7. V6 — bug-class extinction (issue #847)

- `npx tsx script/m61/verify-extinction.ts`
- Proves: every verifier-bug class this program has actually hit (TDZ import,
  silent cap, self-staling byte-gate, concurrent clobber, dynamic import below
  first use, record-after-check) is a **permanent mutant** in a gate that runs in
  the chains. On its first run it found its own class still alive and that was
  fixed, which is the point.

## 8. X1 — program closure (issue #849)

- `npx tsx script/m61/verify-closure.ts`
- Proves: G1 re-executes green, the ledger validates whole, the five IDE-lane
  closures (m24/m29/m42/m44/m55) re-execute green at this HEAD, the 40-gate lane
  ladder record is green **and fresh**, the known-gaps inventory regenerates
  byte-identically, and the spot-check pack names every issue.
- What it does NOT do: close the milestone. That is your verdict.

## Known gaps (generated, never hand-written)

`validation/m61/results/KNOWN-GAPS.md` is regenerated by X1 from the live
records' own declared limitations plus the lint's census and the claim-pins'
coverage residue. A hand edit fails the byte-gate; read that file for the
current, honest list rather than a summary here.

## How to make the verdict

1. `npm run verify:fast` — the declared fast chain, ending with G1–V6.
2. `npx tsx script/m61/verify-closure.ts` — the full closure audit.
3. Pick any record in `validation/m61/results/`, edit a byte, re-run its gate —
   the seal refuses it. That refusal is the milestone working.
4. If the above hold, the milestone is done; if not, the failing check names
   itself. Either way the **verdict is the owner's**, not the gate's.
