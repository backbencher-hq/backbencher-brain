# Hover gap table — verified against the code, per relationship kind

Written by lane 6, task 4. Supersedes the *interpretation* in
`docs/HOVER-KNOWLEDGE-AUDIT.md`, which is a GENERATED file and is not edited by
hand. This document is the hand-checked reading of that file, plus what it
leaves out.

Two different things are called "the gap table" and they disagree:

1. `docs/HOVER-KNOWLEDGE-AUDIT.md` — generated by
   `script/m55/verify-hover-coverage.ts`, a per-symbol table over **6 pinned
   fixture symbols** in an authored 34-file TypeScript fixture. Measured. Real.
   But its denominator is a fixture shape, not the product.
2. The **product** gap: what the canonical 10 relationship kinds at
   `src/mcp/tool-registry.ts:259` (`calls, extends, implements, uses,
   instantiates, overrides, contains, references, imports, exports`) do on the
   hover **as a kind**, on a real index. That is what the owner's question is
   about, and no gate measured it.

Both are below. (2) is derived from the renderer source and is a code reading,
not a measurement — and it says plainly which parts are measured.

## Part 2 — the `12 / 17 = 70.6%` row measures the wrong thing

This is the most consequential error in the audit, and it is the row a reader
would quote.

`relationshipKindsNamedInProse` is built at
`script/m55/verify-hover-coverage.ts:667-668`:

```ts
for (const k of PROSE_KINDS) if (new RegExp(`\\b${k}\\b`).test(card)) kinds.push(k)
```

It greps the rendered card for the **word**. The denominator is
`sum(distinctIncomingKinds.length + distinctOutgoingKinds.length)` summed over
the eight symbols (`:831`) — a per-symbol sum, so `calls` is counted once per
symbol that has it.

Measured against the committed evidence, per symbol:

| symbol | outgoing rows | outgoing kinds stored | "kinds" the metric credits the card with |
| --- | --- | --- | --- |
| `Hub` | 4 | `contains` | `call`, `references` |
| `items` | 0 | — | `call`, `references` |
| `add` | 0 | — | `call`, `references` |
| `count` | 2 | `calls`, `uses` | `call` |
| `reset` | 2 | `references`, `uses` | `call` |
| `notifyHub` | 0 | — | `call`, `references` |
| `hotPath` | 0 | — | `call`, `references` |
| `silent` | 0 | — | — |

Read the second column against the fourth. `items`, `add`, `notifyHub` and
`hotPath` have **zero** outgoing rows and the metric still credits their cards
with naming two kinds. Those words come from ordinary English on the card:

- `references` — the usages header literally reads
  `**usages** — 2 stored references (usage sites only; …)`. It is the section's
  **noun**, naming incoming usage rows, not a `references`-kind relationship.
- `call` — `**connected**: called by [run]` is an **incoming** `calls` row. The
  word `call` there says nothing about what the symbol calls.

And the metric is blind in the direction that matters: **`contains` is the
second most common stored kind in the fixture (4 symbols incoming, 1 outgoing)
and the metric credits it to exactly zero cards** — because there is no prose
word for it. A gap table that scores `references` on seven cards and `contains`
on none is measuring letter frequency, not coverage.

The honest outgoing-side number, computed from the same evidence:

```
outgoing rows known across 8 symbols : 8
outgoing rows rendered WITH a verb   : 1   (count's `calls` row -> "calls countHub")
                                       => 12.5%
```

The four `contains` rows on `Hub`, both rows on `reset` (`references`, `uses`)
and `count`'s `uses` row render **nowhere**.

## Part 2c — the other overstated and understated claims

Checked line by line against the code.

### Call sites: accurate as of this commit

The audit's call-site section is accurate as of this commit. It claims the hover
declines to use `brain_relationship.line_number`. That WAS true before
`e925e9138`; `src/lsp/rich_hover.ts:344-358` now reads it, classifies it
through `src/intelligence/graph/line-address.ts`, and opens the call site. The
measurement above (0 links on a declaration, 15 on a call site) is what the
audit should have said if it were regenerated at this commit — and note the
committed copy still carries the OLD prose, because the generator writes the
prose from a template that was not updated. **`docs/HOVER-KNOWLEDGE-AUDIT.md`
therefore contains a stale paragraph describing a defect that is fixed.** That
is a real documentation defect: a generated doc whose narrative was not
regenerated with its numbers.

### It UNDERSTATES the gap in four ways

1. **The denominator is 17 kinds, not the canonical 10.** The aggregate row
   reads "relationship kinds named 12 / known 17". The 17 is every distinct kind
   the six fixture symbols happen to carry, including analyzer spellings
   outside the canonical list. A reader who takes the canonical 10 from
   `src/mcp/tool-registry.ts:259` cannot reproduce the 70.6%. The generator
   states its denominator in the table caption, so this is not a lie — but it is
   not the denominator the product question asks about.

2. **"44.8% of rows accounted for" mixes two different units.** The numerator
   (13) is *rendered usage locations*. The denominator (29) is *all stored
   relationship rows in either direction*, including outgoing `contains`,
   `uses` and `references` rows that the card has no section for at all. So the
   ratio reads as "the hover shows 45% of what the index knows" when the more
   accurate statement is "the hover renders every **incoming** usage site
   (13/13 of the ones its filter admits) and **none** of the outgoing rows". The
   86.7% row is the honest coverage number; the 44.8% row is an artifact of
   comparing an incoming-only numerator to a both-ends denominator.

3. **The "declared absence" rows hide the largest gap.** For every symbol the
   table has a row `annotations | 0 | none stored — declared absence` and
   `cross-language rows | 0 | none stored — declared absence`. Those rows say the
   **fixture** stores none — which is true and which proves nothing about the
   hover. The fixture authors chose six symbols with no annotations and no
   cross-language facts. On a real index those rows are populated, and the
   audit has no measurement of what the hover does with them.

4. **The one enrichment row is misleading, and it is the row that matters.**
   For `notifyHub` the table reads `rows carrying an enrichment record | 1 | not
   rendered`. Read literally that says the hover ignores enrichment. It does not.
   `src/lsp/rich_hover.ts:439-444` renders enrichment — but only when
   `group.sites.length === 1`:

   ```ts
   if (group.sites.length === 1 && hasDisplayableEnrichment(group.sites[0]!.enrichment)) {
     ...
     groupText += ` · _${desc} (enriched by index${staleNote})_`
   }
   ```

   `notifyHub`'s `called by` group has **two** sites (`run`, `runAgain`), so the
   annotation is skipped by the single-site gate, not by a missing wire-up. That
   the enrichment path works at all is proven by a different gate —
   `H3/R2: connected section carries the enrichment origin label` and
   `H3/R2: enrichment never upgrades the tier line`, both passing in
   `verify-enrichment-surface.ts`. The audit's wording is a **blanket "not
   rendered" where the truth is "not rendered for multi-site groups"**, which is
   the kind of phrasing that gets a working feature deleted.

## Part 3 — the product gap: per canonical relationship kind

Read from the renderer source and cross-checked against the committed evidence
rows. **The "stored in fixture" column is measured; the render columns are a
code reading** — stated as such, per §8.3's "silence is guilt".

The renderer's two verb tables are `OUT_VERB` and `IN_VERB` at
`src/lsp/rich_hover.ts:89-106`. A stored kind with no entry in the applicable
table **cannot appear in the `**connected**:` summary at all** — `connectedGroups()`
at `:398-412` does `?? null` and `continue`s. The usages list is separate: it is
driven by `usageSites()` in `src/lsp/relations.ts`, which admits any INCOMING row
whose kind is not `contains`/`exports`.

| canonical kind | stored in fixture | incoming row → usages list | incoming row → `connected` verb | outgoing row → `connected` verb | verdict |
| --- | --- | --- | --- | --- | --- |
| `calls` | 5 IN / 1 OUT syms | yes | yes — `called by` | yes — `calls` | full |
| `contains` | 4 IN / 1 OUT | **NO** (declaration relationship) | **NO ENTRY** | **NO ENTRY** | **invisible — and it is the 2nd most stored kind** |
| `uses` | 1 IN / 2 OUT | yes | **NO ENTRY** | **NO ENTRY** | **incoming only** |
| `references` | 1 IN / 1 OUT | yes | **NO ENTRY** | **NO ENTRY** | **incoming only** |
| `instantiates` | 1 IN / 0 OUT | yes | yes — `instantiated by` | yes — `instantiates` | full |
| `extends` | never | yes | yes — `extended by` | yes — `extends` | gated by H2, not by this fixture |
| `implements` | never | yes | yes — `implemented by` | yes — `implements` | gated by H2/R3, not by this fixture |
| `overrides` | never | yes | yes — `overridden by` | yes — `overrides` | gated by H2, not by this fixture |
| **`imports`** | **never** | (no verb table entry; not a declaration relationship, so an incoming row would enter the usages list) | **NO ENTRY** | **NO ENTRY** | **UNMEASURED end to end** |
| `exports` | never | **NO** (declaration relationship) | **NO ENTRY** | **NO ENTRY** | invisible, as designed |
| `inherits` (non-canonical, in both tables) | never | yes | yes | yes | not in the canonical list |

Three distinct outcomes, and the distinction matters:

1. **`contains` — invisible, and this is the real hole.** `relations.ts:39`
   correctly excludes it from a symbol's own usage *list*. But there is also no
   `contains` verb anywhere, so an **outgoing** `contains` row — the
   parent-to-member edge, i.e. "what does this class contain" — renders
   nowhere. `Hub` has **4** such rows. For a class, that is the single most
   useful thing a developer can ask, and the hover is silent. This is the
   highest-value remaining gap and it is what task 5 closed.
2. **`uses`, `references` — half-rendered.** An incoming row appears in the
   `usages` list. An **outgoing** row — the symbol uses something, or references
   something — renders nowhere. For `references` that is arguably right (a
   reference is a usage, not a connection). For **`uses`** it is the "what does
   this symbol depend on" half of the owner's question, and it is missing.
3. **`imports` — no verb, no fixture row, no measurement.** In the canonical
   list at `src/mcp/tool-registry.ts:259`, in **neither** verb table, and in
   **zero** fixture rows. Unmeasured end to end. Declared rather than asserted:
   for an incoming row it would enter the usages list (not a declaration
   relationship); for an outgoing row it renders nothing today.

### The owner-facing summary

> "show me what this symbol does"

`connected` answers **which symbols** relate and **by what verb**. On this
fixture that works for 5 of the 10 canonical kinds. The outgoing side — "what does
this call, extend, implement" — works for `calls` and `instantiates` (plus the
four hierarchy kinds, which this fixture does not exercise) and **fails for
`contains`, `uses`, `references` and `imports`**:

```
outgoing rows the index holds across the 8 fixture symbols : 8
outgoing rows rendered WITH a verb                        : 1   => 12.5%
```

`contains` is the worst of the four. For a class, "what does this contain" is
the first question a developer asks, and `Hub` holds **4** such rows that render
nowhere. That is the highest-value remaining gap.

Annotations and cross-language facts have their own card sections and ARE wired
in (`hover.ts:412`, `:417`); they read `none stored` on this fixture because the
fixture authors stored none — declared absence, not a missing wire-up. Staleness
renders (`hover.ts:420`), as do definition, actions and the signature.

So the honest answer to the owner's question is: **the incoming half, yes; the
outgoing half, mostly no** — and the audit's own `70.6%` figure cannot see that,
because it counts English words.

### CORRECTION — an earlier draft of this section was wrong

The first draft of this document asserted that `annotation_ui.ts` and
`cross_language_hover.ts` were "standalone surfaces that the hover never
consumes", on the strength of their file sizes (755 and 114 lines). That was a
guess dressed as a reading, and it is **false**. Checked against the source at
this commit:

```
src/lsp/hover.ts:62   import { storedCrossLanguageRows, factsFromRows, crossLanguageSection } from "./cross_language_hover"
src/lsp/hover.ts:63   import { annotationHoverSection, type AnnotationRow } from "./annotation_ui"
src/lsp/hover.ts:412  if (data.crossLanguageSection ...) lines.push(...)
src/lsp/hover.ts:417  if (data.annotationSection ...) lines.push(...)
src/lsp/hover.ts:515  const crossSection = crossLanguageSection(factsFromRows(storedCrossLanguageRows(raw, symbol.id), file.language))
src/lsp/hover.ts:541  const annotationSection = annotationHoverSection(annotationRows)
```

Both are consumed, and both render on the card. The audit's
`annotations | 0 | none stored` and `cross-language rows | 0 | none stored` rows
are therefore **correct as written**: the *fixture* stores none, the sections
render nothing, and that is declared absence rather than a missing wire-up. The
gate's phrasing — "none stored — declared absence" — was right and this lane's
first reading of it was not.

Recorded rather than deleted, because the error is the useful part: a gap table
verified by reading file sizes is not verified.
