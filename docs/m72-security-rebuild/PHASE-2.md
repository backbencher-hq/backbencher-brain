# M72 Phase 2 — all-language coverage, trust, and `scan` promotion

**Status:** Phase 2a active (fixture oracle + real-corpus M72 evidence + promotion protocol).
Phase 1 (spec engine → `brain_security_flow` → lead answer) is live; see
`docs/m72-security-rebuild/PLAN.md` §2.

## 1. What Phase 2 must prove

Phase 1 gives every executable language **lexical leads** with a declared tier. Phase 2 is
the trust phase: per-language fixtures, a measured oracle, and promotion to `scan` only
where the measurement supports vulnerability vocabulary.

- `leads` — lexical token rules only; output is a lead to validate; no severity claim.
- `scan` — real rules + reachability + per-language fixtures + oracle passing; vulnerability
  vocabulary is allowed and `bb_security` may call the result a finding.
- `unsupported` — no executable source/sink model; the answer must say "not scanned by
  bb_security", never return a clean zero.

Baseline: **0 scan / 39 leads / 14 unsupported (of 53 analyzers)** (Phase 2c; was 36/17 before make was correctly promoted), from
`src/intelligence/security/rebuild/registry.ts` (`formatSecurityTierDeclaration()`).

## 2. Fixture oracle (gate `script/m72/verify-security-fixtures.ts`)

Every `validation/m72/fixtures/<language>/` directory is owner-authored and carries a
README with the expected lead. The gate runs the **real** `analyzeSymbol` engine (whole-file
body in Phase 2a) and asserts:

1. `vulnerable.<ext>` emits at least one lead, and one whose `ruleId` + `vulnerability`
   match the README's `Expected lead: <vulnerability> rule=<rule id>` (severity is also
   asserted where the README declares it);
2. `clean.<ext>` emits **zero** leads;
3. `sanitized.<ext>` emits **zero** leads.

A missing directory, README, expectation, or fixture file is a **FAIL**, never a silent
skip. The gate keeps a negative control (mutated expected rule → red; a lead injected on the
clean fixture → red) and a positive control, so the predicate itself is proven falsifiable.

Evidence: `validation/m72/results/fixtures.json`.

Command:

```bash
npx tsx script/m72/verify-security-fixtures.ts
```

## 3. Real-corpus evidence (regenerated with the M72 engine)

`validation/tools/bb_security/work/probe-real-corpus.ts` drives the real MCP stdio door over
five real repositories (graphql-js TypeScript, rake Ruby, rebar3 Erlang, ansible Python,
sqlite C) and the adversarial cases, then writes `validation/tools/bb_security/REAL-CORPUS.json`.

M72 rules for this evidence:

- counts come **only** from `brain_security_flow`; `brain_taint_flow` is counted solely to
  prove the retired token cross-product is not written by the default path;
- the `parameterized-sql-negative` case must **PASS** (a `$1`-bound parameterized query is
  not a SQL-injection lead); the pre-M72 evidence recorded it as `[critical] SQL injection
  (safe)` with `pass: true`, which is the defect the Phase-0 KNOWN-GAP named;
- an absent corpus is recorded as a **declared absence**, never a fabricated pass;
- counts are generated by the script, never hand-edited.

The old REAL-CORPUS KNOWN-GAP in `script/m72/verify-security-phase0.ts` flips to PASS only
when the regenerated evidence no longer reports the parameterized query as a SQL-injection
lead. The predicate itself is never weakened.

### What Phase 2b still owes (honest remainder)

1. **Per-language precision oracle** (`validation/m72/oracle/<language>.json`) — no language has
   one yet. Today the only measured corpus evidence is the five-repo table above, and four of the
   five corpora produce zero or near-zero leads, so they cannot establish a precision floor.
2. **CVE-fix pairs** — the oracle above needs `(vulnerable commit, fixed commit)` pairs per
   language; none are collected yet. Until then **no language may be promoted to `scan`**, and the
   registry must keep `scan: 0`.
3. **String-interpolation contract extension** — masked literals hide `eval "$1"`, JS `` `${x}` ``
   and Ruby `"#{x}"`. The frozen `LexicalSyntax` has no interpolation field, so this is a contract
   change (Phase 2b), not a spec or engine patch.
4. **Declared empty vs. clean zero** — the zero-row corpora are recorded as *declared empty*
   (engine ran, nothing survived the exclusions). They are not evidence that those repositories are
   free of the corresponding vulnerability classes, and the answer must never be read that way.

## 4. Promotion protocol — `validation/m72/promotions/<language>.json`

A language moves from `leads` to `scan` only when **all** of the following are recorded in one
promotion file and the gates are re-run:

```json
{
  "language": "python",
  "from": "leads",
  "to": "scan",
  "promotedAt": "2026-…",
  "spec": {
    "path": "src/intelligence/security/rebuild/specs/python.ts",
    "sources": 4,
    "sinks": 6,
    "sanitizers": 3,
    "lexical": "comment/string syntax declared"
  },
  "fixtures": {
    "dir": "validation/m72/fixtures/python",
    "gate": "npx tsx script/m72/verify-security-fixtures.ts",
    "evidence": "validation/m72/results/fixtures.json",
    "vulnerable": "expected rule matched; clean=0; sanitized=0"
  },
  "oracle": {
    "corpus": "CVE-fix pairs for this language (Phase 2b)",
    "precision": 0.0,
    "recall": 0.0,
    "floor": "agreed floor for the language, recorded here",
    "evidence": "validation/m72/oracle/<language>.json"
  },
  "gates": {
    "matrix": "npx tsx script/verify-language-tool-matrix.ts",
    "fixtures": "npx tsx script/m72/verify-security-fixtures.ts",
    "phase0": "npx tsx script/m72/verify-security-phase0.ts"
  },
  "knownLimits": ["…"]
}
```

Promotion steps (all mandatory):

1. spec exists with sources, sinks, sanitizers and correct lexical syntax;
2. the fixture gate passes for that language (vulnerable → expected lead, clean → 0,
   sanitized → 0), with the README expectation matching the emitted rule id;
3. the per-language CVE-fix oracle passes the agreed precision/recall floor and its evidence
   is stored under `validation/m72/oracle/<language>.json`;
4. the tier registry is changed in `registry.ts` (single source of truth), the
   language × tool matrix evidence is regenerated, and the generated docs/website data are
   regenerated from the registry — no hand-written capability claim;
5. any regression in 1–4 makes the matrix/fixture gate red and the language reverts to
   `leads`; a promotion is a measurement, not a label.

No language is promoted in Phase 2a: the CVE-fix oracle does not exist yet.

## 5. What remains before `scan`

- **CVE-fix oracle per language (Phase 2b):** curated vulnerable→fixed pairs per language,
  precision/recall measured per language, published per language in
  `validation/m72/oracle/<language>.json`. Only then can `scan` use vulnerability vocabulary.
- **Interpolation contract extension:** the flow engine's reachability covers string
  concatenation and assignment chains; template-literal interpolation (`` `${q}` ``) is not
  yet a proven lead (measured: `f(client.query(\`…${q}\`))` → no lead, while
  `"…" + q` → lead). This must be specified and tested before any language claims
  interpolation coverage.
- **Per-symbol analysis in the fixture gate:** Phase 2a analyses the whole fixture file as
  one body; Phase 2b should parse via `parseFile` and run the engine per symbol so fixture
  expectations match production offsets/symbol ids.
- **Cross-symbol data flow** stays out of scope until a real call/argument edge is modelled
  (PLAN §2 Phase 1 non-goals); a `scan` tier claim must state intra-symbol coverage.
- **Generated-claim wiring:** matrix/docs/website remain generated from `registry.ts`; a
  promotion PR edits the registry and regenerates evidence, never prose alone.
