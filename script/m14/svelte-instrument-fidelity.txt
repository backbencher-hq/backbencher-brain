WHAT THE TWO INSTRUMENTS ACTUALLY DISAGREE ABOUT
  Not the sampling — the sampling is identical and byte-verified. They differ in
  WHICH PATH they call, and that difference is the whole finding:

    firing-check-v2.mjs:146-147,253
        const { getParser } = await import(`${REPO}/src/ast/engine.ts`)
        const pr = await parser.parse(content, f)
        const res = new Cls().analyze(pr.rootNode, content, f)   // <-- NO 4th arg

    engine.ts:1592-1623  (inside ASTEngine.parseFile)
        if ((language === "vue" || language === "svelte") && tree?.rootNode) {
          ... sfcScriptTrees / sfcScriptLines / sfcScriptCols / sfcScriptLangs
          context = { ...context, sfcScriptTrees, ... }
        }

  The SFC seam — which pre-parses every <script> body with the JS/TS/TSX grammar —
  lives INSIDE ASTEngine.parseFile. The instrument never calls parseFile, so it calls
  analyze() with context === undefined, so at real-svelte-analyzer.ts:739

        const scriptTrees: Tree[] = context?.sfcScriptTrees ?? []

  is [], and the ENTIRE script half of the analyzer is skipped: no script sub-parse,
  no imports[], no exports[], no script symbols, no script calls, no runes, no $props.
  What survives is the template pass alone, which can only ever produce
  instantiates + on:/render/directive calls + snippet contains. That is exactly the
  3/10 it prints.

  Production does not take this path. src/ast/pool-worker.ts:833 calls
      engineModule.ASTEngine.parseFile(filePath, content, context)
  and that is the path every indexed symbol and relationship in the brain comes from.
  The workstream doc says so too: "EMITTED — production parseFile (from
  src/ast/pool-worker.ts, NOT analyze())".

  So for an SFC analyzer the instrument labelled "production path
  (getParser -> parse -> analyze)" is measuring a path production does not take. It is
  a correct number about the wrong population — the shape M14's honesty contract calls
  the most dangerous kind of number.
