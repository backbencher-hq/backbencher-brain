# `validation/` — evidence, not documentation

Everything under this directory is **evidence produced by a gate or by a recorded review**: JSON results written
by `script/verify-*.ts` / `script/mNN/verify-*.ts` runs, and markdown pages that state findings, measurements
and rulings with citations. It is not a user guide; user documentation lives in `docs/` (start at
[`docs/README.md`](../docs/README.md)).

## Rules that keep it usable as evidence

- **Gate output is written by the gate.** Result JSON files are regenerated by their gate; edit the gate or fix
  the code, never hand-edit the JSON. If you need to know how a number was produced, the gate header names the
  population, command and method.
- **Human review pages are dated claims, not current contracts.** A verification page records what was checked
  at a commit; later behaviour may legitimately differ. Current contracts live in `docs/`.
- **Every number carries its provenance.** Pages cite the command that produced a measurement and the artifact
  that holds it (for example `validation/m14/results/M14.0.F5.json`). A stale path is reported, not hidden.
- **Superseded measurements are preserved, never deleted.** During the one-branch consolidation, when a
  measurement conflicted with another branch the newer one was kept and the other was preserved byte-for-byte
  beside it with a `.superseded-*` suffix, mapped in the directory's `SUPERSEDED-MANIFEST.md`. Do not delete
  these because they look like duplicates; that ruling is deliberate evidence provenance.
- **Tracked means load-bearing.** `script/m14/verify-self-contained.ts` checks that imports, grammar WASM and
  lane inputs the machinery actually reads resolve to tracked bytes; `validation/m14/verification/
  TREE-SELF-CONTAINMENT.md` records the tree-cleanup ruling and what was deliberately left local-only.

## Layout

| Path | Contents |
| --- | --- |
| `validation/mNN/` | Results and review pages for milestone NN (the analyzer campaign is `m14/`; the IDE work is `m25/`) |
| `validation/m14/fixtures/<language>/` | Pinned analyzer fixtures and their expectation files (the F3 guard) |
| `validation/m14/spec/` | Analyzer specs the completeness inventory and gates read |
| `validation/m14/verification/` | Human-readable findings, audits, rulings and closure records |
| `validation/tools/<tool>/` | Per-tool audit evidence and logs |
| `validation/mNN/results/` | Machine-readable gate results; regenerated by running the gate |

## Reproducing a result

Each gate's header comment names its command and population, for example:

```bash
npx tsx script/verify-index.ts                    # indexer suite -> validation/... results
npx tsx script/m14/verify-analyzer-docs.ts        # analyzer documentation census
bun script/m14/verify-fleet.ts                    # 50-lane guard matrix (Bun)
```

Some suites need a writable data directory (`BB_DATA_DIR=…`) or a corpus checkout; the gate says so when it
skips or fails for that reason. Runtime differences are declared: the pool gates exercise Node worker/fork
semantics and say so when run under Bun.
